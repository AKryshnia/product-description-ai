# AI-помощник для подготовки товарных описаний

MVP сервиса, который по данным об одном контрольно-измерительном приборе формирует **черновик
товарной карточки** для B2B-интернет-магазина: SEO-заголовок, SEO-описание, структурированные
характеристики, поисковые запросы и коммерческий блок. Текст генерирует GigaChat; технические
значения берутся **только из входных данных**, а результат проходит программную проверку.

> Это черновик для контент-менеджера, а не готовая публикация. Автоматическая проверка
> достоверности эвристическая: она находит расхождения с входными данными, но **не доказывает**,
> что текст верен и не гарантирует отсутствия выдумок. Карточку даже со статусом `ok` перед
> публикацией проверяют вручную (см. «Что означает статус» и «Известные ограничения»).

## Стек

Python 3.12 · FastAPI · Pydantic v2 · pydantic-settings · официальный SDK `gigachat` · pytest · ruff.
БД, очередей, RAG, LangChain и фронтенда нет: для ручной проверки достаточно Swagger UI.

## Архитектура

```
POST /generate ─▶ main.py          маршруты, единый формат ошибок
                    │
                    ▼
                 service.py        оркестрация: анализ → генерация → проверка → (одна) корректировка
                    ├─ completeness.py   полнота и согласованность входа (до обращения к LLM)
                    ├─ generator.py      промпт и разбор ответа модели
                    ├─ validator.py      формат, SEO-ограничения, достоверность  (опирается на facts.py)
                    │    └─ binding.py   привязка значений к характеристике, исполнению и условию
                    ├─ export.py         Markdown
                    └─ llm.py            универсальный интерфейс LLMClient + единые ошибки
                          ▲
                          └─ providers/gigachat.py   ЕДИНСТВЕННЫЙ код, знающий про GigaChat и его SDK
```

Ключевые правила:

* **Python владеет фактами.** Список характеристик в ответе — копия входных данных; ответ модели на
  него не влияет (поле `specs` в ответе модели игнорируется).
* **LLM пишет только тексты:** заголовок, описание, запросы, коммерческий блок.
* **Граница доверия.** Достоверными источниками значений считаются характеристики (`specs`) и
  название. `description` — повествовательный текст: значение, найденное только в нём, автоматически
  не подтверждается, а предложение-команда не подтверждает собственные значения.
* **Если данных нет вообще** (ни значений характеристик, ни описания) — модель не вызывается.
* **Не более одной** корректирующей генерации; результат с неподтверждённым техническим значением
  не выдаётся (блок скрывается), остальное сохраняется.

### Независимость от провайдера LLM

Бизнес-логика зависит только от `app/llm.py` (интерфейс `LLMClient`, `Capabilities`, `LLMResult`,
иерархия `LLMError`) — там нет ни SDK, ни форматов конкретного провайдера. Провайдер выбирается
переменными `LLM_PROVIDER` и `LLM_MODEL`.

Чтобы подключить другого провайдера (реализован и проверен только GigaChat):

1. Создать `app/providers/<имя>.py` с классом, у которого есть `model`, `capabilities` и
   `complete(messages, *, json_schema=None) -> LLMResult`. Адаптер сам переводит сообщения в формат
   провайдера, вызывает API и **переводит его ошибки** в `LLMAuthError`, `LLMRateLimited`,
   `LLMTimeout`, `LLMUnavailable`, `LLMAPIError`, `LLMInvalidResponse`, `LLMUnsupported`.
2. Добавить фабрику в словарь `PROVIDERS` (`app/providers/__init__.py`); импорт SDK — внутри
   фабрики, чтобы не выбранный провайдер не требовал установки SDK.
3. Добавить в `app/config.py` поля доступа (по образцу `GIGACHAT_*`) и указать `LLM_PROVIDER`.

Не меняются: API-контракты, схемы, `service`, `generator`, `validator`, `export`, основной набор
тестов. Различия возможностей описываются полем `capabilities` (сейчас одно: `json_schema`; для
GigaChat оно `False` — проверено на реальном API, см. ниже). Неизвестный `LLM_PROVIDER` не роняет
приложение: `/generate` отвечает `503 llm_not_configured` с перечнем доступных провайдеров.

**От GigaChat зависят:** `app/providers/gigachat.py`, поля `GIGACHAT_*` в `app/config.py`,
`scripts/live_check.py` (режимы `--models` и `--probe-structured`), каталог `certs/`.

## Настройка GigaChat API

1. **Ключ авторизации.** В личном кабинете GigaChat API получите *ключ авторизации*
   (строка в base64) и впишите его в `.env` как `GIGACHAT_CREDENTIALS`. Файл `.env` в git не попадает.
   Если доступ не для физлица, поменяйте `GIGACHAT_SCOPE` на `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP`.
2. **Корневой сертификат Минцифры.** Сертификат GigaChat не входит в системные хранилища, поэтому
   без него TLS-проверка завершится ошибкой (`self-signed certificate in certificate chain`).
   Проверку **отключать нельзя** — скачайте корневой сертификат из официального источника:

   ```bash
   mkdir -p certs
   curl -fsSL https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt \
        -o certs/russian_trusted_root_ca_pem.crt
   openssl x509 -in certs/russian_trusted_root_ca_pem.crt -noout -subject -fingerprint -sha256
   ```

   При проверке (06.11.2026) сертификат имел вид:
   `CN = Russian Trusted Root CA`, срок действия до 27.02.2032, SHA-256
   `D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31`.
   Сверьте отпечаток с официальной страницей Минцифры/Госуслуг. Путь указывается в
   `GIGACHAT_CA_BUNDLE_FILE` (по умолчанию `certs/russian_trusted_root_ca_pem.crt`).
3. **Модель.** По умолчанию `GigaChat-2-Pro`. Список моделей, доступных вашему ключу:
   `python scripts/live_check.py --models`. Сменить модель — переменная `LLM_MODEL`.
4. **Базовый URL.** По умолчанию `https://gigachat.devices.sberbank.ru/api/v1` (проверен). В новой
   документации Сбера встречается `https://api.giga.chat/v1` — из сети, где проверялся проект, он
   недоступен, поэтому по умолчанию не используется (`GIGACHAT_BASE_URL`).

### Что означает статус

`status` — итог **автоматической** проверки, а не оценка достоверности текста:

| `status` | Значение |
|---|---|
| `ok` | Замечаний не найдено: каждое число, единица и обозначение в тексте сопоставлены с характеристикой входа, условия и контекст им не противоречат, известных неподтверждённых формулировок нет. **Это не подтверждение достоверности.** |
| `needs_review` | Текст выдан, но программа не смогла что-то подтвердить: значение из свободного описания, потерянное условие или опция, противоречивый контекст, неподтверждённая формулировка (`warnings`/`missing_info` с `severity: review`). |
| `partial` | Есть нарушения или часть результата не сформирована: длина, число запросов, пустые аудитория/задачи, скрытый блок с неподтверждённым значением, данных недостаточно. |

Что `ok` **не** гарантирует: правильность смысловых утверждений без чисел (конкретизация аудитории,
«средняя масса» вместо «масса», материал, описанный другими словами), отсутствие устаревших или
неточных данных в самом входе и грамотность текста. Поэтому ручная проверка перед публикацией
обязательна при любом статусе; `needs_review` — нормальный исход, а `ok` не означает «можно
публиковать автоматически».

### Коды ответов

| HTTP | `error.code` | Когда |
|---|---|---|
| 200 | — | Карточка сформирована (любой `status`, в т. ч. `partial`) |
| 400 | `invalid_json` | Тело запроса — не JSON |
| 413 | `payload_too_large` | Тело запроса больше 1 МБ |
| 422 | `invalid_input` | Неверные типы, пустое `name`, слишком большие данные; в `details` — поля без значений |
| 429 | `llm_rate_limited` | Лимит запросов провайдера (есть `Retry-After`, если сообщил провайдер) |
| 501 | `llm_unsupported_capability` | Адаптер не поддерживает запрошенную возможность |
| 502 | `llm_auth_failed`, `llm_unavailable`, `llm_api_error`, `llm_invalid_response` | Отказ в доступе, сеть/TLS/недоступность сервера (в т. ч. сервера авторизации), ошибка API, неразбираемый ответ провайдера |
| 503 | `llm_not_configured` | Нет ключа, нет файла сертификата, неизвестный `LLM_PROVIDER` |
| 504 | `llm_timeout` | Тайм-аут провайдера |
| 500 | `internal_error` | Непредвиденная ошибка (без подробностей наружу) |

## Промпты

Системный промпт — отдельный читаемый файл **`app/prompts/system.md`**; его можно править без
изменения кода. Числовые ограничения (`{title_max}`, `{description_min}` и т. п.) подставляются из
валидатора, поэтому промпт и проверка не расходятся. Промпт не зависит от провайдера.

Ключевые решения:

* **Формат JSON задаётся инструкцией, а не `response_format`.** Проверено на реальном API
  (`python scripts/live_check.py --probe-structured`; для другой модели — с `LLM_MODEL=…`):
  `GigaChat-2-Pro`, `-2-Max` и `-Pro` при
  `response_format: json_schema, strict: true` вернули обычный текст, а инструкция в промпте дала JSON.
  Поэтому параметр не отправляется (`Capabilities.json_schema = False`), а ответ разбирает и
  проверяет приложение.
* **Граница «данные / инструкции».** Данные товара передаются JSON внутри `<product_data>`; символы
  `<` и `>` экранируются, поэтому текст из данных не может «закрыть» блок. Системный промпт
  объявляет блок недоверенным и запрещает выполнять команды из него.
* **Объём без выдумок.** Для описания задана структура: назначение → *каждая* характеристика
  по шаблону «название — значение» → нейтральные рекомендации по выбору и заказу, которые ничего не
  утверждают о приборе. Добавлены пары «плохо/хорошо» с плейсхолдерами: запретов («без оценок»)
  модели оказалось недостаточно.
* **Одна корректирующая генерация.** Модели возвращается её ответ и список конкретных замечаний
  с фрагментами; выбирается лучший из двух вариантов (меньше нарушений, затем — ближе к диапазону длины).
* **`temperature = 0.0`.** Измерено на одном примере (N=3): при 0.2 длины описания 773/802/697 и
  статусы `partial ×2, needs_review ×1`; при 0.0 — 835/827/835 и `needs_review ×3`. Значение
  задаётся `LLM_TEMPERATURE`.

## Контроль достоверности

1. **Анализ полноты (до LLM)** — `completeness.py`. Отсутствует производитель/описание/характеристики
   (`info`); пустые значения (`review`); противоречия (`review`): одна характеристика с разными
   значениями, диапазон в обратном порядке, описание противоречит характеристике; неизвестные поля;
   фрагменты, похожие на инструкции для ИИ. Применимость характеристик к типу прибора **не
   предполагается**: сообщается только о ключах, которые переданы без значения.
2. **Что считается фактом (граница доверия)** — `facts.py`, `binding.py`.
   * *Характеристики и название* — структурированные источники. Значение оттуда подтверждает
     совпадающее значение в тексте.
   * *Описание* — повествование. Оно остаётся источником назначения и общих сведений (слов), но
     **число, единица или обозначение, найденные только в нём, не считаются подтверждёнными**: если
     модель их использовала, карточка получает `review` (`narrative_only_value`) — сверьте с
     паспортом. Сведения о сертификации и стандартах (`сертифик…`, `ГОСТ`, `стандарт`) подтверждаются
     только характеристиками.
   * *Предложения-команды* («Добавь в описание…», «Игнорируй правила…», «Редактору: итоговая
     карточка должна…») исключаются из фактов — и из описания, и из значений характеристик, — а
     входной анализ сообщает о них (`manual_check`). Признак — известные формулировки команд и общий
     признак «предложение адресовано результату или редактору и содержит обязательность». Такой
     перечень неполон по природе, поэтому защита на нём не держится: непризнанная команда всё равно
     не сделает значение подтверждённым — оно останется «только из описания». Защита от внедрения
     инструкций **не абсолютна**: слова (не значения) из непризнанной команды могут пройти.
3. **Проверка результата** — `validator.py` и `binding.py`; три исхода: *подтверждено*, *нарушение*
   (`error`), *на ручную проверку* (`review`).

   **Есть ли такое значение во входе:**
   * число отсутствует → `error`; **знак — часть значения** (`−40` и `+40` разные; «минус 50»
     и «плюс 60» словами читаются как `−50` и `60`); число, записанное словом («три», «ста»), → `review`;
   * сочетание «число+единица» не найдено → `review`; единица, которой нет во входе, → `error`;
     единицы словами («градусов Фаренгейта») приводятся к символам и проверяются так же;
   * дробная запись («1,0») там, где во входе только целое («1») → `review`;
   * обозначения и латинские слова, которых нет во входе → `review`.

   **К тому ли значению оно отнесено** (`binding.py`): для каждого числа и обозначения ищутся места
   входа с тем же значением и сравниваются слова рядом:
   * *условие* — значение с условием («(в металлическом корпусе)», «при +25 °C», «при сопротивлении
     не более 10 Ом» в названии) должно нести его в тексте. У составного условия («при +23 °C и
     влажности 50 %» — два ограничения; делят «и», «;», запятая с пробелом) в тексте должно быть
     названо **каждое** ограничение: сохранённой одной части недостаточно. Среди вариантов одной
     характеристики сравниваются только отличительные слова («металлическом», а не общее «корпус»)
     → `condition_dropped`;
   * *опция* — значение из списка вариантов или опций нельзя выдать за основное: в тексте должно
     быть название списка («по заказу», «опционально»). Опцией значение делает название
     характеристики («опции по заказу», «варианты исполнения», «дополнительно») либо три и более
     пункта через «;»; один пункт под названием «опции по заказу» остаётся опцией
     → `condition_dropped`;
   * *граница* — «не более 0,8 кг», «не менее 0,8 кг», «менее», «более», «до», «от» — разные
     утверждения; граница у одиночного числа должна сохраниться, а её потеря («масса 0,8 кг» вместо
     «не более 0,8 кг») считается расхождением. У конца диапазона «от 5 до 25 Гц» нижняя граница —
     5, верхняя — 25: «не более 5 Гц» → `bound_mismatch`, «до 25 Гц» верно;
   * *целостность диапазона* — диапазон или перечень значений должен быть записан во входе целиком:
     «0–16 бар» не подтверждается тем, что есть «0–6 бар» и «10–16 бар». Если отдельные числа во входе
     есть, а такой записи нет, результат не «подтверждён», а «не удалось подтвердить» →
     `combination_unconfirmed`;
   * *соседи* — если соседние слова описывают другую характеристику с другим значением («рабочая
     температура» при значении температуры хранения, «фаза-нуль» вместо «фаза-фаза») →
     `value_context_mismatch`;
   * *источник* — значение только из описания → `narrative_only_value`.

   **Прочее:** слово с противоположным смыслом: приставка (`неагрессивных` → `агрессивных`) или
   частица перед словом («не поддерживается» → «поддерживается», и наоборот); «не только» и «не
   превышает» отрицанием слова не считаются; материал или
   отсутствие свойства («из латуни», «без обслуживания»), которых нет во входе; рекламные формулировки,
   отрасли, места и условия применения, которых нет во входе (фразой, не основой: «технологическая
   черта» не оправдывает «технологические процессы»; «различных помещениях» — не обобщение, а
   «различных условиях эксплуатации» — обобщение); задвоения вроде «0,1 % %».

   **Формат:** заголовок ≤ 70, описание 800–1200, запросов 3–5, без дублей; в коммерческом блоке
   обязательны содержательные `audience` и `tasks` (`scenarios` может быть пустым, если сценарии
   входом не подтверждены). Пустое поле и поле, где только заглушка («нет сведений», «данных нет»,
   «уточняется», «не применимо», «не указано», «N/A» — регистр, пробелы и пунктуация не важны),
   считается отсутствующим. Предложение со смыслом, где есть «не» или «нет» («прибор не требует
   обслуживания»), заглушкой не является.
4. **Реакция на нарушения.** Любое замечание запускает одну корректирующую генерацию. Если
   `error` по числам или единицам остался — блок **не выдаётся**, статус `partial`. Нарушения длины и
   пустой коммерческий блок не скрывают текст, но дают `partial` с причиной; блок **не заполняется
   выдуманными аудиторией и задачами**. Достоверность важнее длины: при недостатке данных объём
   не набирается домыслами.

**Подсчёт символов:** `len()` строки Python, т. е. кодовые точки Юникода, после схлопывания
пробельных последовательностей в один пробел; пробелы и знаки препинания учитываются.

### Обращения к модели и расход токенов

`generation.llm_calls` — сколько раз **приложение** обратилось к модели (0, 1 или 2), включая
корректирующий вызов, который закончился ошибкой или тайм-аутом. Не входят: HTTP-повторы внутри SDK
(`LLM_MAX_RETRIES`) и обновление OAuth-токена. `prompt_tokens`/`completion_tokens` — сумма по
**полученным** ответам; расход вызова, не вернувшего ответ, неизвестен и в сумму не входит, поэтому при
сбое корректировки токены могут быть занижены.

### Ошибки провайдера и журнал

Адаптер переводит сбои SDK в типизированные `LLMError`; неожиданные ошибки приложения не
маскируются. Ответ провайдера, который SDK не смог разобрать (не JSON, неожиданная структура,
OAuth без срока жизни токена), даёт `502 llm_invalid_response`, а не `500`. Отказ в доступе на
этапе OAuth (`400`/`401`/`403`; неверный ключ реальный API отклоняет кодом `400`) — `llm_auth_failed`;
недоступность сервера авторизации (`5xx`) — `llm_unavailable` без совета менять ключ; `429` —
`llm_rate_limited`. В журнал попадают только тип ошибки, этап (`oauth`/`chat`/`response`) и
HTTP-код: тела ответов, токены и их фрагменты не логируются (проверено тестами на транспортном
уровне, где настоящий SDK разбирает подставные HTTP-ответы).

### Бенчмарки

**Валидатор (офлайн, детерминированно)** — `tests/test_validator_benchmark.py`
(`pytest tests/test_validator_benchmark.py -s`). Размеченный корпус: 15 корректных фрагментов и 41
фрагмент с выдумкой, включая фразы, реально встретившиеся в ответах GigaChat. Результат:
**ложных срабатываний 0/15, полнота 39/41 (95%)**. Два пропуска оставлены в корпусе намеренно и
показывают слепые зоны: число, совпавшее с цифрой из названия («в 2 раза» при `DM 02`) и число прописью,
совпавшее с другим значением («сто» = `100 мм`).

**Привязка значений** — `tests/test_binding_benchmark.py`. 32 верные формулировки по четырём
каталожным товарам и автоматические подмены: значение заменяется на другое значение той же размерности
из этого же товара. Результат: **верных фраз с замечаниями 0/32, подмен замечено 38/51 (75%)**. Подмену
не видно, когда соседние слова подходят к нескольким характеристикам сразу (общее «температура») или
значение из той же характеристики переставлено внутри её перечня.

**Контрольный набор** (`tests/test_binding.py`) — 25 фраз с размеченной по смыслу истиной
(`C01–C08`, `B01–B17`) и 5 карточек с допустимым ответом модели. До исправления привязки значений: найдено 4 из 17 искажений, 1 ложное
срабатывание, все 5 карточек получили `ok`. После: найдено 17 из 17, ложных 0 из 8, ни одна из 5
карточек `ok` не получила. Набор использовался при разработке исправления, поэтому теперь он —

**Составные утверждения** — `tests/test_compound_claims.py` и `tests/test_catalog_claims.py`. Класс за

## Известные ограничения

* **Проверка достоверности эвристическая и частичная.** Она сопоставляет числа, единицы,
  обозначения и контекст рядом; смысл предложения она не понимает. Не ловятся: качественные слова при
  верном значении («рабочий», «средняя масса»), выдуманная аудитория и задачи без чисел и
  стоп-слов, опция, названная «исполнением» без слов «по заказу», условие, снятое словами («при любом»),
  производитель, которого нет во входе, число, совпавшее с числом из названия или с другой величиной,
  когда рядом нет различающих слов. Стоп-слова подобраны по наблюдаемым ответам GigaChat; для другой
  модели список придётся пересмотреть.
* **Ручная проверка обязательна всегда:** `ok` означает «автоматическая проверка замечаний не нашла».
* **Сведения только из `description` не подтверждаются автоматически.** Если характеристик нет, а
  числа есть лишь в описании, любое их использование даёт `needs_review`. Защита от внедрения
  инструкций не абсолютна.
* **Разброс результата модели** между запусками; текст из малого числа характеристик часто не
  набирает 800 символов без «воды» — такая карточка честно получает `partial`.
* **Условия** распознаются, если они стоят в скобках после значения с единицей, после «при …» либо
  в названии характеристики после «при …»; вариантов-опций — это название с «опции», «по заказу»,
  «варианты», «дополнительно» либо три и более пункта через «;». Две альтернативы одной величины
  различаются по словам условия. Каждое ограничение составного условия проверяется только в
  пределах того же предложения: условие, вынесенное в соседнее предложение, получит замечание.
* **Граница и отрицание проверяются у соседних слов.** Граница читается из слов прямо перед одиночным
  числом («не более», «до», «от»): «максимальная масса 0,7 кг» вместо «не более 0,7 кг» даст
  замечание; границу, которой нет во входе («не более 0,8 кг» при входном «0,8 кг»), программа не
  сверяет, как и конец диапазона, названный без границы («частота 25 Гц» из «от 5 до 25 Гц»).
  Отрицание ловится, если «не» стоит прямо перед словом; синонимы («присутствует» вместо
  «не поддерживается») и «не всегда поддерживается» не распознаются.
* **Заглушки коммерческого блока** распознаются, если ими заполнено всё поле; заглушка рядом с
  содержательным пунктом поле не «опустошает» и в карточке останется, а заглушка со словами
  («уточнить у производителя») не распознаётся.
* **Числительные словами** распознаются в пределах 2–20, десятков до 40 и «сто»; единицы словами —
  по списку основных (давление, длина, напряжение, ток, температура и т. п.).
* **Языковая проверка отсутствует:** склеенные предложения, канцеляризмы и т. п. остаются на
  контент-менеджере.
* **Один провайдер проверен.** Интерфейс провайдеро-независим, но промпт и стоп-слова настроены и
  проверены только на `GigaChat-2-Pro`. Другие провайдеры не реализованы и не проверялись.
* **Не проверено вживую:** ответ `429` (лимит запросов), сбой OAuth `5xx` и неразбираемый ответ — только
  на подменах HTTP-уровня.
* `api.giga.chat` из сети проверки недоступен; работа с ним не проверялась.
* Данные двух реальных приборов в задании не приложены; примеры 02–04 — демонстрационные и вымышлены.
